# Languages (internationalization)

The product speaks English, Spanish (`es`) and Croatian (`hr`). This doc holds the rules every string, in this
repo, in the pages repo and in both native apps, is written against. Read it before adding user-visible text.

**Scope.** What the product itself says: page chrome, feedback, errors, labels, mail, push, PDFs. What a person
types (a trip's title, a note, a chat message) is never translated. A trip is hosted in ONE language
(`Trip.language`) and its own data stays in that language; only its page can have other-language versions.
Right-to-left languages are out of scope.

## The registry: `model/Language`

`Language` is the one list of languages, for the interface AND for trips. Each constant carries the language's
name in its own words, its `Locale`, and its BCP 47 tag (`getTag()`, looked up with `Language.forTag`). A trip
stores the constant's NAME (`Language.named`); everything about the interface (a person's preference, a
cookie, `Accept-Language`, a bundle suffix, a page-version suffix) uses the TAG. Never invent a second list.

Adding a language:

1. A constant in `Language` (declaration order is display order; never rename one, trips store the name).
2. A file per bundle with the tag as suffix, and the same for the apps' catalogs.
3. The plural categories the language needs in every plural message (below).
4. A supported-locale entry in the pages repo's `faces-config.xml`.
5. A native reviewer. Until they sign off, the language stays off (next section).

## Switching a language on: `site.languages`

`KnownSettings.SITE_LANGUAGES` lists the tags a site offers, first one the default, and an organization may
override it for its own site. It ships as `en`, so code for a new language deploys dark and is switched on per
site once its translations are reviewed. `i18n/SiteLanguages.parse` reads the value: unknown tags are dropped
and an empty result is English, so a typo can never leave a site with no language.

## Who decides the language

In order: an explicit choice (the switcher, or `?lang=`), the signed-in person's saved preference, the
browser's or app's `Accept-Language`, the site's default, English. The language of the trip being viewed never
changes the interface around it. Mail and push go out in the RECIPIENT's language, never the sender's or the
request's, so background work always passes a locale explicitly.

The switcher and `?lang=` only set the browser's `lang` cookie; they never write the person's saved preference.
Any page could carry such a link (an image in a typed description loads it for every signed-in reader), so the
saved language, which mail and push follow, changes only through the profile's Language field or
`PUT /api/people/{id}/language`, both protected and audited (`web/RequestLocale`).

### Who reads each mail and document

`i18n/ReaderLanguage` answers for a reader: `of(person, trip)` for a traveler (their saved choice, else the
trip's language, else the organization's default), `ofStaff` / `ofStaffAddress` for staff (their own saved
choice, else English: the trip's language never decides for the office). A language counts only where the
sending organization's site offers it; a shared mailbox, or a list of addresses, reads English. Audit lines stay
English whatever anyone reads.

| What | Reader | Language |
|------|--------|----------|
| Chat mentions, replies, photo comments, daily digest | the member, or the family manager for a child | `of` |
| Payment, failed-payment and checkout values (`PaymentMailer`), the approval mail's ticket line | the payer / the traveler | `of` |
| Sign-in code (`LoginCodeCommands`) | the person signing in | the request's (they are on the page); off a request, `of(person, null)` |
| New registration and cancellation notices, the "Moved Registration" and "Tx saved" subjects | the configured notice address | `ofStaffAddress` |
| New account notices (`AuthResource`, `account/createAccount.xhtml`) | the account notice address | `ofStaffAddress` (pages: `#{text.forStaff(address, trip, key, ...)}`) |
| Account-deletion notice | each organization's notice address | `ofStaffAddress`; the audit fallback is English |
| Support requests | each support admin | `ofStaff` |
| Content reports | the report recipient | `ofStaffAddress` |
| Expense report to the treasurer, mail and PDF | the treasurer address | `ofStaffAddress`, one language throughout (`ExpenseCommands.reportPageIn`) |
| Expense report PDF download (page, REST) | the person downloading | the request's |
| Signed document copy (`WaiverCommands.signedPdf`) | anyone who may read it | the TRIP's language, so every copy of the record reads alike; the sign page and the apps show the two attestations in the signer's own |

A body that IS an audit line (the "Moved Registration" and "Tx saved" notices) stays English under a translated
subject. The mail merge's computed fields, which it shares with trip reminders (`ReminderRecipients.tripFacts`),
write the trip's dates and the balance due date in the TRIP's language, the one its messages are written in
(`Formats.dateSpan`, English unchanged); the passport sentences are still English. The admin-managed templates'
own words are their author's.

## Writing a message

- **Whole sentences.** One key holds one complete sentence or label. Never build a sentence from fragments,
  joins or `+`: word order differs between languages and a fragment cannot be translated.
- **Arguments, not concatenation.** Values go in as named or numbered arguments of an ICU message
  (`i18n/MessageText.format`), which the translator may reorder.
- **Plurals use plural rules.** English and Spanish have two forms, Croatian has three (1 dan, 2 dana,
  5 dana), so a `count == 1` branch or a "(s)" is a bug. Write
  `{count, plural, one {# day} other {# days}}`; Croatian supplies `one`, `few` and `other`.
- **Embedded names stand alone.** Croatian changes a noun's ending by its role in the sentence. A sentence that
  embeds a person's name or anything typed by a user is worded so the value needs no ending: a label and a
  colon ("Registering: Lucy") or the subject position ("Lucy is registered").
- **One key per meaning (DRY).** The same text with the same meaning uses ONE key; shared vocabulary (Save,
  Cancel, Delete, Close, Yes, No) lives under `common.`. The exception: one English word with two meanings or
  roles ("Open" the action, "Open" the status) gets two keys, because it will not share a translation.
  `MessageBundlePolicyIT` (pages repo) fails on repeated words: list a deliberate second key in its
  `SAME_WORDS_OTHER_MEANING` with the reason. Keys the code builds from a prefix (enum labels, setting labels)
  repeat on purpose and are exempt by prefix; text meaning the same thing as one of them reads that key.
- **Dates and numbers** are formatted for the reader's language, never with a fixed pattern. **Money is the
  exception**: US dollars in US format (`$1,234.56`) in every language.
- **Codes stay codes.** A REST error keeps its stable `error` code; only its `message` is translated. Wire
  values, enum names and stored ids are never translated or renamed.
- English is the source language, in US spelling, with "--" and never an em dash.

## Dates and numbers

**The rule.** A date, a time or a count a person reads takes the READER's format: the requester's language on a page or
in a REST answer (`RequestContext.currentLocale()`), the recipient's in mail, push and PDFs (the `Locale` the caller
already holds). **Money does not**: US dollars in US format in every language (`pay/MoneyMath`; a page's
`f:convertNumber` for money carries `locale="en_US"`, and a money `p:inputNumber` carries `decimalSeparator="."
thousandSeparator=","`, since PrimeFaces otherwise takes both from the view's language and a Spanish reader would type
"12,50" into a field that means $1,250). **Machine formats never change**: stored values, audit text, logs, file names,
CSV/TSV exports, ISO wire values, cache and dedupe keys, and anything parsed back keep their fixed pattern. A plain ISO
date or time on an admin page (`yyyy-MM-dd HH:mm`) is language-neutral and stays.

**Skeletons, not patterns.** A fixed pattern such as `MMM d, yyyy` is English word order with translated month
names. Write a *skeleton* instead, which names the fields and their widths and nothing else, and let the locale
supply order and separators (`i18n/Formats`):

| Skeleton | English | Spanish | Croatian |
|----------|---------|---------|----------|
| `yMMMd` | `MMM d, yyyy` | `d MMM yyyy` | `d. MMM yyyy.` |
| `yMMdd` | `MM/dd/yyyy` | `dd/MM/yyyy` | `dd. MM. yyyy.` |
| `MMMd` | `MMM d` | `d MMM` | `d. MMM` |
| `jm` | `h:mm a` | `H:mm` | `HH:mm` |

- Java: `Formats.format(when, "yMMMd", locale)`, or `Formats.formatter(skeleton, locale)` for a
  `DateTimeFormatter` (add `.withZone` as needed); `Formats.dateRange(start, end, "yMMMd", locale)` writes two
  days as one range with the shared parts once ("3–12 sept 2026").
- Pages: `<f:convertDateTime pattern="#{text.datePattern('yMMMd')}" .../>`, and a date picker's
  `pattern="#{text.datePattern('yMMdd')}"`. A picker's pattern also decides how a TYPED date is read, so a
  Spanish reader types day first. A time picker takes `hourFormat="#{text.hourFormat}"` and
  `pattern="#{text.timePickerPattern}"` together. A masked birthdate (`p:inputMask` "99-99-9999") keeps its
  mask, which fits either order, and reads with `pattern="#{text.birthdatePattern}"` and the placeholder
  `#{msg['common.birthdatePlaceholder']}`: month first in English, day first in every other language.
- **English never changes.** A one-letter year is widened to `yyyy` and CLDR's narrow no-break space before
  AM/PM becomes a plain space, so the common skeletons give exactly the English patterns the product always
  printed (`FormatsTest` pins each one in use). Where no skeleton does ("Sep 3 3:05 PM" without a comma,
  `MM-dd-yyyy`, a time with "at"), pass the old pattern as English's own:
  `Formats.format(when, "MMMdjm", "MMM d h:mm a", locale)`, `#{text.datePatternOr('MMMdjm', 'MMM d h:mm a')}`.
  The same goes for a range: each English caller keeps its own shape, and only other languages use
  `Formats.dateRange`.
- A date inside an English-only sentence (one not yet moved to a bundle) stays English until its sentence is
  translated: a Spanish date in an English sentence helps nobody.
- Numbers: `Formats.number` / `#{text.number(n)}` for a count a person reads; numbers inside an ICU message are
  formatted by the message already. In the browser, `Intl.DateTimeFormat(document.documentElement.lang, ...)`.

## Where the words live

`i18n/Text` reads a key's bundle from its first segment: `common.save` is in `i18n/common.properties` (English,
the source) with `common_es.properties` and `common_hr.properties` beside it. Bundles are UTF-8 classpath
resources. This repo holds the code's words and the shared vocabulary (`common`) in
`trip/src/main/resources/i18n/`; the pages repo holds page copy in `webapp/WEB-INF/classes/i18n/`. Both end up
on the webapp's classpath, so a page reads `common.*` exactly as the code does. A missing translation reads the
English value; a missing key renders `???key???` and logs once.

| Bundle | Repo | Holds |
|--------|------|-------|
| `feedback` | this | page messages raised by beans (`PageFeedback`) |
| `api` | this | REST error and status sentences |
| `labels` | this | enum display names (`labels.enum.TripKind.PILGRIMAGE`), setting labels and descriptions |
| `mail`, `push`, `pdf` | this | outbound text, always formatted for the RECIPIENT's locale |
| `server` | this | what the server's own classes say outside beans and REST resources: HTML cleaner notes, content types, checkout and upload refusals, processor and domain checks |
| `common` | this | shared vocabulary: Save, Cancel, Name, Amount (one key per meaning); read by code AND pages |
| `chrome` | pages | templates, menu, topbar, footer, sidebar, consent banner |
| `account`, `trip`, `pay`, `chat`, `lodging`, `content`, `reports`, `admin`, `help` | pages | one per page family |
| `fieldhelp` | pages | the "i" help cards: `fieldhelp.{page}.{field}.title` and `.text` |
| `js` | pages | strings the browser scripts show (`window.TripText`) |

Key shape: `{bundle}.{page or dialog}.{what}` in lowerCamel segments, named for what the text IS, never for where
it sits or what it says today (`trip.edit.saveDraft`, not `trip.edit.button3` or `trip.edit.saveDraftButtonText`).

## In a page

- No arguments: `#{msg['trip.edit.title']}`. Inside another expression it is just a value:
  `#{canSave ? msg['account.person.editTitle'] : msg['account.person.title']}`.
- With arguments: `#{text.format('chrome.viewing', person.preferredName)}` over `Viewing: {0}`. Never
  `#{msg['x']} #{name} #{msg['y']}`: that is a sentence built from fragments.
- A trailing colon, a required-star or other decoration stays in the page: `#{msg['common.name']}:`.
- A sentence with a link or a bold word INSIDE it keeps its markup in the bundle value and is written
  `<h:outputText value="#{text.html('help.x.intro', name)}" escape="false"/>`: `text.html` HTML-escapes every
  argument, so only the bundle's own markup is markup. With NO arguments it is `#{msg['help.x.intro']}` with
  `escape="false"`: there is nothing to escape, and one spelling keeps the pages alike. Do not name such a key
  with `note`, `title` or `description` (the unescaped-output check reads those as typed text). Plain sentences
  never use it.
- A value's LEADING spaces are dropped when a bundle is read, and a missing argument prints as nothing. Spacing
  that matters (a space before a following component) stays in the page as `&nbsp;` or literal text.
- A count the BROWSER computes (a countdown) cannot use a server-side plural: a script picks the form itself
  (next section).
- Dates and numbers: `#{text.date(when)}`, `text.longDate`, `text.time`, `text.dateTime`, `text.number`.
  Money stays as it is.
- Language names (`Language.displayName`) and anything a person typed are never keyed.
- `#{text.languageTag}` is the page's `lang`; a block of a trip's own text keeps `lang="#{trip.languageTag}"`,
  and a content page's sections carry `lang="#{pageVersions.languageTagOf(pageKey)}"`, the language of the
  version shown (its own, when it fell back; blank, an unknown language, for an "original page" as below), so
  a screen reader never reads it in the reader's language.
- When moving existing text to a key, the English VALUE stays byte-identical to what the page said, so every
  test that reads the page still passes. Rewording is a separate change.

## In a script

What a browser script shows (a confirm, an alert, a label it builds, a status line) is in the pages repo's `js`
bundle, keyed `js.{script or page}.{what}`, and read through `window.TripText`.

- **Where it comes from.** `WEB-INF/template.xhtml` includes `WEB-INF/tripText.xhtml` first thing in the head, so
  every page on the template has it before any script runs. That include writes ONE inline script holding the
  whole `js` bundle and the `common` words it lists, in the request's language, as JSON from
  `#{text.scriptMessages('common.cancel ...')}`, which escapes `< > &`, both quotes and U+2028/2029 so no value
  can end the string or the script element. It
  reads nothing but the request (no session, no view), so anonymous pages carry it too. The embed page
  (`trip/tripPage.xhtml`) has no template and no scripts.
- **Reading a message.** `TripText.get('js.chat.rejoin')`; with arguments `TripText.get('js.chat.onBehalfOf',
  author, member)` over `{0} on behalf of {1}`. A `js` value is NOT an ICU pattern: the script fills `{0}`,
  `{1}` itself, and an apostrophe is just an apostrophe. A missing key shows `???key???`.
- **Shared words.** A script's Cancel, Remove or "{0} of {1}" is the page's `common` key
  (`TripText.get('common.cancel')`), added to the list in `tripText.xhtml` (not all of `common`: every page's
  source would carry words it never shows, and tests that read a page's source would find them).
  `MessageBundlePolicyIT` fails on a shared word a script reads that the list lacks. A word that already lives
  in another PAGE bundle is handed to the script by
  the page instead, in a `data-*` attribute written with `#{msg[...]}` (the floor map's "Not saved", the
  drawer's "All"), never copied into `js`.
- **Counts.** Write one key per plural category, `js.chat.newMessages.one` / `.other` (Croatian adds `.few`):
  `.other` always, and the other categories a language needs. `TripText.plural('js.chat.newMessages', n)` picks
  with `Intl.PluralRules` for the page's `lang`, falls back to `.other`, and passes `n` as `{0}` (further
  arguments are `{1}`, `{2}`). A `count === 1` branch or a "(s)" is still a bug.
- **Whole sentences.** A sentence the script used to glue ("1 new message", "Light " + ratio, `' at ' + origin`)
  is one message with arguments. Never build a key from parts: every key is a literal in the script, which is
  what lets `MessageBundlePolicyIT` check that each key a script names exists and each `js` key is read.
- **In a page's handler.** `onclick="return confirm(TripText.get('js.chatSettings.removePersonConfirm'));"`,
  never `#{msg[...]}` inside a JavaScript string, which would need JavaScript escaping that EL does not do.
- **Dates and times** a script formats use `Intl.DateTimeFormat` with `document.documentElement.lang`, never
  `toLocaleString()` with no language (the browser's own locale, which differs between a test and a reader).
  English keeps its old shape: the chat's "7/29/2026 6:48 PM", with a plain space before AM/PM.
- **The rich-text editor's own words** (Jodit's buttons, dialogs and prompts) are Jodit's, keyed by its English
  strings: Jodit ships Spanish, and the pages repo's `resources/trip-js/richEditorLang.js` adds Croatian (formal)
  and moves Jodit's Spanish from "usted" to "tú". A new toolbar button or dialog checks both. The editor picks the
  language from the page's `lang`.
- **Not covered.** The service worker (`sw.js`) has no page, so a notification's text comes from the server
  (the `push` bundle, in the recipient's language). The local-mode payment stand-in (`fakeStripe.js`) is test
  scaffolding and stays English.

## Language versions of a page

Authored pages (an organization's home page and Site Pages, the shared and marketing pages, a trip's page) are
translated by their AUTHORS, not by bundles: `content/PageVersions`.

- A version is a **whole, independent page**: its own section key, rows and history. Its key is the page's key
  plus `@` and the language tag (`page:org:{uuid}:about@es`). The page written first keeps its unmarked key, so
  adding versions moves no stored row. Containers' children hang off instance ids, so nothing below a page's
  top-level rows knows about languages.
- **Which version a request reads** is decided where the key is made: `site.pageKey`, `site.pageKey(name)` and
  `site.tripPageKey(id)` answer the version's key (`PageVersionCommands.forThisRequest`), so hosts, the edit
  drawer and saves need no other change. The reader's language picks the version; a language with nothing
  written falls back to the WHOLE unmarked page, never a mix. `?version=es` names a version outright, which is
  how an editor opens one that is still empty.
- **A page's own language** (what the unmarked key is written in) is the site's default language, or for a
  trip's page the TRIP's language. Both can change after versions exist. A version marked with what is NOW the
  own language is then that language's page (`PageVersions.resolve`), and the unmarked page, written in whatever
  the own language used to be, becomes the "original page": still every unwritten language's fallback, its
  language no longer known (`languageTagOf` answers blank), and given a tab of its own at the end of the bar,
  opened with `?version=original` (`PageVersionCommands.ORIGINAL`). Nothing records which language it was.
- **Tenancy and rights are the page's**: `OrgPageBootstrap.orgOf` / `tripOf` strip the mark before parsing, so a
  version is gated by exactly the grants its page is, and there is no cross-organization fallback.
- **Authoring**: in edit mode, on a site offering two or more languages, the bar at the top of the page
  (`WEB-INF/contentSections.xhtml`) lists the versions; an empty one offers "Start from a copy of the page"
  (`ContentCommands.copyPage`, a deep copy with new ids) and a written one "Delete this version"
  (`deleteVersion`; a page's own key is never deleted this way).
- Which trips a site's home page lists is still read from the UNMARKED home page (`ListingScope`): a version's
  own Trip Listings sections decide what that version shows, not what the site reaches
  (`ListingScopeTest.aLanguageVersionOfTheHomePageDoesNotChangeWhatTheSiteLists`).
- **The "How to pay" page** resolves its version like any other page: `payPage.ensurePage` seeds the starter text
  into the page's own key only, then answers `forThisRequest` of it, so the version bar works there too.
- **Search engines**: a page with at least one written version beyond its own emits, in the head
  (`WEB-INF/template.xhtml`), `<link rel="alternate" hreflang="..">` per written language (this same address with
  `?lang=`) plus `x-default` (the address with no language), from `pageVersions.alternates(pageKey)` and the key the
  content host froze at initPage. A page without versions, and every page of a one-language site, emits nothing.

- **Email templates** have language versions too, on the same `@{tag}` convention (`registration-received@es`), and
  are resolved for the RECIPIENT's language: `docs/content-templates.md`, "Language versions of an email". The
  shipped Spanish and Croatian versions of the starter emails were reviewed with the bundles. A trip's reminder
  messages are written per trip in the trip's language and are not versioned; only the words the code adds
  around them (the test send's "[Test]" marker, `mail.reminder.testSubject`) come from a bundle.

### Short texts an organization writes per language

Not every authored word is a page. Two kinds of short text are written per language by the organization:

- **Site Page titles**: `SitePage.titles` (language tag to title; `title` stays the one in the site's default
  language, and an older row has none). The menu (`WEB-INF/menu.xhtml`) and a page's browser title (`page.xhtml`)
  read `orgPages.titleOf(page)`: the reader's language, else the default title. Written in the Site Pages dialog
  (`admin/orgPages.xhtml`), one field per other language the site offers (`orgPages.otherLanguages`). A new
  site's starter pages (About Us, Board of Directors) come with Spanish and Croatian menu titles, from
  `content/starter-site-pages.json`; their content is English only (`docs/org-admin.md`, "Starter pages").
- **Site text settings**: a setting `KnownSettings` declares `.withTranslatable()` (declared once there:
  `site.title`, `site.sidebar.title`, `site.footer.title`, `site.footer.text`, `site.donate.title`,
  `site.donate.text`) may carry an override key with a language mark, `site.footer.text@es`, in
  `Organization.settingsOverrides`. `ConfigCommands` (the org rung of `getString(def, org)`) reads the key for the
  request's language BEFORE the plain one; a blank or missing one is the plain text. Only org-overridable STRING
  settings can be translatable (`TranslatedSettingsTest` holds every declaration to that): a URL, a color or a
  number means the same in every language, and `saveOrgSettings` refuses a language key on anything else. The
  organization settings page (`admin/orgConfig.xhtml`) shows one more field per other offered language under
  each such setting (the generic rows and the Appearance tab's Site details), bound into the same map by key:
  simpler than a language selector, since every language is visible at once, nothing on the page changes state,
  and each tab's Save already carries every key it shows (`OrgSettingsTabs.valuesFor`, `BrandCommands.forSave`).
  `home.banner.text` is not one: it is a site-only setting with no organization rung, so there is no org row to
  hold its translations.

Spanish is neutral Latin American, not a regional variant. Form of address (formal or informal "you") is the
reviewer's call, made once per language and recorded here: **Spanish: informal "tú"** (the product text the owner
reviewed and approved on 2026-11-21 uses it throughout: "Escribe", "Ingresa", "tu cuenta"). **Croatian: formal "vi"
everywhere** (owner, 2026-11-21: the usual form in Croatian software), as both native apps already have it:
"vaš", "Prijavite se", "nemate", lowercase "vi"/"vaš" mid-sentence. Short button and menu labels keep the
short imperative the apps use ("Spremi", "Odustani", "Pokušaj ponovno"), and sign-in/out read "Prijavite se" /
"Odjavite se". The pages repo's `CroatianFormalAddressPolicyIT` holds every `*_hr.properties` value of both repos
to this: it flags informal forms in running text, and lets a label under 8 words keep its short imperative (a
button named inside a sentence is quoted: "Odustani"). Mail templates, the native apps' catalogs and seeded
content are outside it and stay a reviewer's job.
